# 실제 서비스 AI 설계·운영 가이드 사이트 개편 설계서

- 작성일: 2026-07-31
- 상태: 사용자 방향 승인 완료, 사이트 구현 전 검토 대기
- 대상 화면: `/ai-guide`
- 호환 주소: `/ai-blueprint`, `/formulas`
- 대상 계열사: 현대웰니스, 현대리바트, 현대그린푸드

## 1. 설계 목적

기존 AI 가이드와 수식 설명을 실제 서비스 개발자가 순서대로 읽을 수 있는 하나의 운영 설계 가이드로 재구성한다. 독자는 AI·머신러닝·RAG 경험이 없는 팀원으로 가정한다.

페이지를 모두 읽으면 다음 질문에 답할 수 있어야 한다.

1. AI 기능이 어떤 순서로 실행되는가?
2. 각 단계에 어떤 데이터가 필요한가?
3. 머신러닝, 규칙, 수식, LLM, RAG, 벡터 검색은 각각 무엇을 담당하는가?
4. 계열사와 카테고리 차이는 하나의 공통 모델에 어떻게 반영되는가?
5. 데이터 부족·신규 상품·트렌드 급등·동기화 실패 등 상황에서 어떻게 처리하는가?
6. 수요예측 결과가 위험점수와 전략 수식에 어떻게 연결되는가?
7. 최종적으로 화면과 서버가 어떤 값을 받아야 하는가?
8. 실제 결과로 모델과 정책을 어떻게 검증하고 개선하는가?

## 2. 고정된 서비스 경계

### 2.1 데이터 소유권

- 현대웰니스 Oracle, 현대리바트 Oracle, 현대그린푸드 Oracle은 각 계열사의 상품·재고·판매 원본을 소유한다.
- 통합 시스템 Oracle은 공통 형식으로 변환한 복제 데이터와 AI 입력·예측·위험·전략·설명·검증 결과를 소유한다.
- 통합 시스템은 계열사 DB에 등록·수정·삭제하지 않는다.
- 계열사 DB는 읽기 전용 계정과 연동 전용 View를 제공한다.
- 통합 시스템은 하루 1회 자동 동기화하며, 권한 있는 사용자가 필요할 때 수동 갱신을 요청할 수 있다.
- 수동 갱신은 비동기 작업으로 실행하고 중복 실행을 차단한다.

### 2.2 AI와 외부 시스템의 경계

- 서비스는 주문·결제·배송·상품 등록을 실행하지 않는다.
- 서비스는 판매·입고·할인·프로모션·처리 전략을 계산하고 설명한다.
- 실제 실행은 외부 판매·운영 시스템에서 이루어진다.
- 외부 시스템의 실제 판매·반품·잔여재고·마진 결과를 회수해 예측과 전략을 검증한다.
- LLM은 가격·수량·위험점수·이익을 임의로 만들거나 변경하지 않는다.

## 3. 선택한 AI 구조

### 3.1 모델 분리 원칙

계열사별로 동일한 머신러닝을 세 번 구현하지 않는다. 초기에는 기능별 공통 모델을 사용하고 계열사·카테고리·상품 특성을 입력값으로 제공한다.

```text
공통 수요예측 모델
+ 계열사 ID
+ 카테고리 ID
+ 상품·SKU 특성
+ 가격·프로모션·트렌드
+ 계열사·카테고리별 보정값
+ 계열사별 정책·비용 프로필
```

특정 상품군에서 공통 모델의 오차가 반복적으로 크고 별도 모델의 개선 효과가 시간순 검증에서 재현될 때만 해당 상품군 모델을 분리한다. 계열사 이름만으로 모델을 분리하지 않는다.

### 3.2 기술별 책임

| 구분 | 담당 책임 | 담당하지 않는 책임 |
| --- | --- | --- |
| SQL·통계 | 현재 재고, 판매속도, 변화율, 급등·급락 탐지 | 미래 판매량의 복합 예측 |
| 머신러닝 | 미래 수요, 할인·프로모션 반응, 선택적 확률 예측 | 법규 판단, 정확한 금액 계산, 승인 |
| 정책·규칙 엔진 | 법규·검사·소유권·할인 한도·데이터 품질 차단 | 판매량 생성, 자연어 설명 |
| 수식 엔진 | 위험점수, 매출, 비용, 회피비용, 증분이익, 후보 순위 | 문서 검색, 자유로운 추론 |
| RAG | 정책·법규·상품 지침·과거 사례 근거 검색 | 재고·매출 숫자 조회, 금액 계산 |
| 벡터 검색 | 표현이 다른 유사 문서 검색 | 정형 데이터 집계와 필터링 |
| LLM | 계산 결과의 쉬운 설명, 주의사항, 확인 질문, Teams 요약 | 수치 결정, 하드 차단 변경, 자동 승인 |

## 4. 페이지 정보 구조

기존 `/ai-guide`, `/ai-blueprint`, `/formulas`는 동일한 통합 콘텐츠를 보여준다. 주 탐색 메뉴에는 `/ai-guide` 하나만 노출하고 다른 주소는 기존 링크 호환을 위해 유지한다.

페이지는 다음 순서로 구성한다.

1. 페이지 목적과 전체 AI 처리 흐름
2. 기술별 책임 구분
3. 전체 필요 데이터 목록
4. 계열사·카테고리별 입력 차이
5. 단계별 AI 처리 설계
6. 상황별 처리 플레이북
7. 머신러닝 학습·검증·배포 흐름
8. 수식 적용 위치와 입력 출처
9. LLM·RAG·벡터 검색 흐름
10. 실패·대체 처리와 재현성
11. 최종 결과 데이터 계약
12. 출처와 확정 전 확인사항

페이지 상단에는 위 순서의 짧은 단계 탐색을 제공한다. 각 주요 섹션은 별도 앵커를 가져 직접 이동할 수 있어야 한다.

## 5. 전체 AI 처리 흐름

첫 번째 핵심 시각 요소는 다음 순서를 보여준다.

```text
계열사 데이터 수집
→ 공통 데이터 변환
→ 데이터 품질 확인
→ 트렌드 신호 생성
→ 머신러닝 수요예측
→ 계열사·카테고리별 보정
→ 하드 차단 확인
→ 위험점수 계산
→ 전략 후보 생성
→ 매출·비용·증분이익 계산
→ 목표별 전략 순위
→ RAG 근거 검색
→ LLM 설명
→ 실제 결과 비교
→ 모델·정책 개선
```

각 단계는 펼침 카드로 제공하며 다음 항목을 동일한 순서로 표시한다.

- 단계가 하는 일
- 반드시 필요한 입력
- 선택 입력
- 적용 기술
- 생성하는 결과
- 데이터 부족 또는 실패 시 처리
- 다음 단계에 전달하는 값

## 6. 전체 필요 데이터 목록

### 6.1 데이터 등급

모든 입력은 다음 세 등급으로 표시한다.

- 필수: 없으면 계산 또는 추천을 차단한다.
- 정확도 향상: 없어도 기준모델·기본값으로 처리할 수 있지만 신뢰도를 낮춘다.
- 후속 고도화: 충분한 이력이 쌓인 뒤 확률 모델이나 RAG에 사용한다.

### 6.2 공통 데이터 묶음

| 데이터 묶음 | 주요 값 | 등급 | 사용 단계 |
| --- | --- | --- | --- |
| 식별정보 | 계열사·법인·카테고리·상품·SKU·로트·채널·원천키 | 필수 | 전체 연결과 권한·집계 |
| 시간정보 | 발생시각·기준시각·영업일·요일·계절·행사기간 | 필수 | 수요예측·재현 |
| 판매정보 | 순판매량·취소·반품·품절·판매가·할인액 | 필수 | 학습 정답·판매속도 |
| 재고정보 | 현재고·예약수량·가용재고·입고예정·보관일 | 필수 | 예측 상한·위험·잔여재고 |
| 가격·행사 | 정상가·판매가·할인율·쿠폰·포인트·프로모션 노출 | 필수 | 조건별 수요와 매출 |
| 비용정보 | 수수료·배송·설치·보관·반품·파손·폐기·행사비 | 필수 또는 전략 차단 | 전략 손익 |
| 상품 특성 | 소비기한·보관조건·검사·회수·옵션·상품 유형 | 계열사별 필수 | 하드 차단·특성 예측 |
| 트렌드 | 검색·SNS·조회·찜·장바구니·변화율·출처·수집시각 | 정확도 향상 | 트렌드·수요예측 |
| 정책 | 판매 가능 여부·최대 할인율·최소 잔여기한·허용 채널 | 필수 | 하드 차단·후보 생성 |
| 실제 결과 | 실제 판매량·반품·잔여재고·실제 마진·실행 상태 | 필수 운영 피드백 | 검증·재학습 |
| 재현정보 | 데이터 snapshot·모델·수식·정책·피처 버전 | 필수 | 감사·재현·롤백 |
| 문서 | 법규·정책·상품 지침·과거 검토 사례 | 후속 고도화 | RAG·LLM 근거 |

### 6.3 값의 출처 표시

각 값은 화면에서 다음 중 하나로 구분한다.

- 계열사 원천 확정값
- 통합 시스템 계산값
- 머신러닝 예측값
- 정책 기본값
- 사용자가 시뮬레이션에서 변경한 값
- 미수집 또는 대체 처리된 값

## 7. 계열사·카테고리 적용

### 7.1 현대웰니스

- 주요 특성: 성분·기능·대상 고객·소비기한·보관조건·표시·회수 상태
- 주요 트렌드: 성분명·기능 관심·건강 이슈·검색·내부 조회
- 하드 차단: 표시·회수·판매 가능 상태·최소 잔여기한·데이터 품질
- 주요 비용: 포장·검수·반품·회수·보관·폐기
- 수요예측 특성: 소비기한은 예측 정답이 아니라 판매 가능 상한과 위험 입력으로도 사용한다.

### 7.2 현대리바트

- 주요 특성: 옵션·상품 유형·가격대·보관일·채널·비용 프로필
- 주요 트렌드: 인테리어·이사·혼수·시즌·공간별 관심
- 하드 차단: 판매 정책·원가/비용 누락·할인 한도·소유권
- 주요 비용: 배송·설치·보관·파손·재배송·반품·AS
- 수요예측 특성: 판매 빈도가 낮은 SKU는 카테고리·가격대·옵션 패턴을 공유한다.

### 7.3 현대그린푸드

- 주요 특성: 로트·소비기한·온도구분·검사·이력추적·채널
- 주요 트렌드: 메뉴·제철·날씨·검색·내부 주문·판매
- 하드 차단: 검사·소비기한·온도·이력추적·회수·판매 가능 상태
- 주요 비용: 콜드체인·피킹·포장·보냉재·반품·폐기
- 수요예측 특성: 신선·냉장·냉동·가공 카테고리별 예측 기간과 보정값을 분리한다.

## 8. 단계별 AI 처리 설계

### 8.1 데이터 수집·변환

- 입력: 계열사별 연동 View
- 처리: 원천키 보존, 공통 ID 매핑, 단위·시각·코드 변환
- 결과: 통합 상품·SKU·로트·재고·판매·가격·비용 snapshot
- 실패: 해당 계열사의 마지막 성공 snapshot을 유지하고 데이터 지연 상태를 표시

### 8.2 데이터 품질

- 검사: 필수값 누락, 중복, 음수 수량, 가격 오류, 판매-재고 시각 불일치, View 계약 변경
- 결과: 통과, 경고, 차단 상태와 사유
- 차단: 판매량·재고·가격·정책의 필수 조합이 없으면 마진 전략을 만들지 않는다.

### 8.3 트렌드 신호

- 초기 방식: 변화율·이동평균·강건 Z점수로 급등·급락 탐지
- ML 적용: 트렌드가 실제 판매량에 미치는 영향을 수요예측 모델이 학습
- 결과: 상승·유지·하락, 신호별 변화율, 출처, 기준시각, 신뢰 상태
- 주의: 상대 검색지수를 절대 검색량으로 표시하지 않는다.

### 8.4 수요예측 머신러닝

- 모델 단위: 공통 전역 모델
- 식별 피처: 계열사·카테고리·상품 유형·채널·SKU
- 시계열 피처: 판매 지연값·이동통계·품절·가격·프로모션·요일·계절
- 외생 피처: 검색·SNS·조회·날씨 등 검증된 신호
- 결과: 기간별 보수·기본·낙관 예상 판매량, 예측 구간, 데이터 충분성
- 상한: 전략 적용 가능 수량은 가용재고를 넘지 않는다.
- 보정: 계열사·카테고리별 반복 편향을 검증된 보정값으로 조정

### 8.5 하드 차단

- 머신러닝을 사용하지 않는다.
- 소유권·법규·표시·검사·기한·정책·데이터 품질을 고정 규칙으로 평가한다.
- 하나라도 미통과하면 이익이 높아도 후보에서 제외한다.

### 8.6 위험점수

- 공통 수식에 계열사·카테고리별 가중치와 임계값을 적용한다.
- 수요예측은 판매속도·소진일·미소진 위험을 계산하는 입력이다.
- 결과에는 총점뿐 아니라 신호별 기여값과 적용 정책 버전을 저장한다.

### 8.7 전략 후보와 시뮬레이션

- 허용된 수량·할인율·기간·쿠폰·채널·프로모션 조합만 생성한다.
- 조건 변경 시 모델을 재학습하지 않고 학습된 모델로 조건별 수요를 다시 추론한다.
- 수식 엔진이 매출·변동비·회피비용·잠식·위험손실·기준선을 계산한다.
- 최대마진·빠른소진·최대매출·위험최소화 목표별 순위를 제공한다.

### 8.8 RAG·LLM

- 숫자는 Oracle 조회와 모델·수식 결과만 사용한다.
- RAG는 정책·법규·상품 지침·과거 사례 문서만 검색한다.
- LLM은 구조화된 결과와 검색 근거로 추천 이유·주의사항·확인 질문을 생성한다.
- 근거가 없으면 추정하지 않고 `확인 가능한 근거 없음`을 반환한다.

### 8.9 실제 결과 검증

- 예상과 실제 판매량·잔여재고·증분이익을 비교한다.
- 품절·노출 부족·경쟁 행사·운영 미실행처럼 모델 밖의 원인을 코드로 기록한다.
- 모델 오차와 전략 실행 오차를 분리한다.
- 재학습과 보정값 변경은 검증 결과와 모델 버전으로 관리한다.

## 9. 상황별 처리 플레이북

상황별 카드는 `상황 → 판단 → 처리 → 화면 표시 → 다음 행동` 순서로 구성한다.

### 9.1 신규 상품

```text
판매이력 없음
→ 계열사·카테고리·가격대·상품 특성으로 유사 집단 선택
→ 공통 모델의 집단 패턴 사용
→ 넓은 예측 범위와 낮은 신뢰 상태 표시
→ 자동 최적안 확정 없이 담당자 확인 요청
```

### 9.2 판매이력 부족

- 기준모델과 카테고리 평균을 함께 계산한다.
- 복잡한 모델 결과가 기준모델보다 검증되지 않으면 기준모델을 사용한다.
- 사용 데이터 기간과 부족한 값을 표시한다.

### 9.3 트렌드 급등

- 검색·SNS만 상승한 경우 관심 신호로만 표시한다.
- 조회·판매가 함께 상승하면 수요 상승 피처로 강화한다.
- 재고·리드타임·기한·예측 하방을 확인한 뒤 `추가 입고 검토` 또는 프로모션 후보를 제시한다.
- 자동 발주하지 않는다.

### 9.4 트렌드 급락

- 판매량과 조회도 하락하면 미소진·악성재고 전환 가능성을 높인다.
- 가격·프로모션·채널·처리기한 후보를 비교한다.
- 일시적 계절 변화인지 반복 하락인지 함께 표시한다.

### 9.5 소비기한 임박

- 판매 가능 최소 잔여기한을 먼저 검사한다.
- 통과한 로트만 예상수요와 처리 전략을 계산한다.
- 기한 안의 잔여재고와 예상 폐기비를 핵심 결과로 표시한다.

### 9.6 느린 판매·높은 재고

- 품절 보정 판매속도와 예상수요로 재고일수를 계산한다.
- 할인·기간·채널 조건별 미소진량과 증분이익을 비교한다.
- 높은 재고금액만으로 위험을 확정하지 않는다.

### 9.7 할인 이력 부족

- 상품별 반응 대신 계열사·카테고리의 검증된 평균 반응을 사용한다.
- 예측 범위를 넓히고 할인 반응 데이터 부족을 표시한다.
- 손실 가능성이 큰 할인안은 담당자 확인 대상으로 낮춘다.

### 9.8 낮은 예측 신뢰도

- 신뢰도를 예상수량에 직접 곱하지 않는다.
- 보수·기본·낙관 범위와 손익분기 조건을 함께 표시한다.
- 하방 증분이익이 음수인 후보에는 경고를 표시한다.

### 9.9 계열사 동기화 실패

- 실패 계열사에 마지막 성공 snapshot과 지연 시간을 표시한다.
- 최신성이 기준을 넘으면 새로운 전략 생성을 차단한다.
- 다른 계열사의 동기화·조회·예측은 계속한다.

### 9.10 정책·검사·소유권 차단

- 모델 예측과 손익 계산보다 먼저 차단한다.
- 차단 사유와 근거 정책을 표시한다.
- LLM은 차단을 완화하거나 우회하는 전략을 생성하지 않는다.

### 9.11 사용자의 조건 변경

- 할인율·기간·수량·쿠폰 조건을 새로운 시나리오 입력으로 저장한다.
- 최신 승인 모델로 조건부 수요를 다시 추론한다.
- 동일 snapshot과 정책 버전으로 수식을 재계산해 원안과 차이를 표시한다.

### 9.12 예상과 실제의 큰 차이

- 예측 오류, 데이터 오류, 실행 미준수, 외부 사건을 분리 기록한다.
- 모델 문제가 확인된 경우 이전 모델과 비교 검증 후 보정 또는 재학습한다.
- 수식이나 정책 문제는 모델 재학습으로 해결하지 않는다.

## 10. 머신러닝 생명주기

```text
학습 snapshot 생성
→ 미래 데이터 누출 검사
→ 기준모델 학습
→ 공통 ML 모델 학습
→ 시간순 검증
→ 계열사·카테고리별 평가
→ 보정값 평가
→ 기존 운영 모델과 비교
→ 승인 모델 등록
→ 배치·수동 갱신 시 추론
→ 실제 결과 모니터링
→ 재학습 또는 롤백
```

### 10.1 학습 정답

- 기준일 이후 7일·14일 등 합의된 기간의 품절 보정 순판매량
- 반품·취소를 분리한 수량
- 상품군별 예측 기간은 정책으로 관리

### 10.2 검증 기준

- 무작위 분할이 아니라 시간순 검증을 사용한다.
- 전체 평균 외에 계열사·카테고리·판매량 구간별 오차를 표시한다.
- MAE·WAPE·MASE 계열 지표와 예측구간 포함률을 함께 본다.
- 복잡한 모델이 기준모델보다 안정적으로 좋아야 운영 후보가 된다.

### 10.3 모델 분리 조건

- 특정 상품군의 오차가 여러 검증 기간에서 반복된다.
- 별도 모델이 충분한 표본에서 반복적으로 개선된다.
- 판매 단위·예측 기간·피처 구조가 공통 모델과 실질적으로 다르다.
- 분리 후 학습·배포·모니터링 비용을 감당할 수 있다.

## 11. 수식 연결 설계

수식은 한글 용어로 보여주고, 각 항목 옆에 값의 출처를 표시한다.

```text
머신러닝 기본 예상수요
→ 가용재고 상한 적용
→ 전략별 예상 판매수량
→ 전략 매출·전략 변동비
→ 피할 수 있는 보관·폐기비
→ 잠식·위험 손실
→ 기준선 차감
→ 증분 기여현금이익
```

각 수식 카드에는 다음을 표시한다.

- 한글 수식
- 쉽게 말한 뜻
- 필요한 입력값
- 입력값의 출처
- 계열사별 차이
- 결과 사용처
- 값이 없을 때의 처리
- 적용한 수식 버전

## 12. LLM·RAG·벡터 검색 설계

### 12.1 구조화 데이터와 문서 분리

- 수량·가격·재고·비용·점수·예측: Oracle과 계산 API
- 정책·법규·상품 지침·과거 검토 의견: RAG 문서 검색
- 의미 기반 문서 검색이 실제로 필요할 때만 벡터 검색을 추가

### 12.2 LLM 입력 계약

- 상품·계열사·카테고리 식별정보
- 데이터 기준시각과 충분성
- 보수·기본·낙관 예측
- 차단 결과와 근거
- 위험 신호별 값
- 전략 조건과 손익 구성
- RAG가 찾은 문서 제목·구간·링크

### 12.3 LLM 출력 계약

- 한 문장 요약
- 권장 행동
- 숫자로 확인되는 근거
- 하방 위험
- 부족한 데이터
- 담당자가 확인할 질문
- 근거 문서 링크

출력은 정해진 JSON 구조로 검증하고, 입력에 없는 수치가 생성되면 폐기한다.

## 15. 화면 표현 원칙

- 용어는 한글을 기본으로 하고 개발용 영문 필드는 보조 설명에서만 표시한다.
- 긴 페이지는 상단 단계 탐색과 섹션 앵커로 이동할 수 있어야 한다.
- 전체 흐름은 가로 단계와 모바일 세로 흐름 모두 읽을 수 있어야 한다.
- 상세 정보는 `details/summary` 또는 접근 가능한 펼침 카드로 제공한다.
- 표는 작은 화면에서 가로 스크롤을 제공하고 첫 번째 핵심 열을 식별하기 쉽게 유지한다.
- 색만으로 정상·경고·차단을 구분하지 않고 텍스트 배지를 함께 표시한다.
- 키보드로 모든 펼침 카드와 링크를 조작할 수 있어야 한다.
- 수식 블록은 줄바꿈을 유지하고 긴 내용은 카드 너비 안에서 스크롤 또는 줄바꿈한다.
- 기존 출처 링크는 관련 단계 가까이에 유지한다.

## 16. 기존 사이트 콘텐츠 정리

### 유지

- 공통 모델과 정책 프로필 원칙
- 계열사별 상품·비용·위험 차이
- 공통 DB·확장 프로필 설명
- 한글 수식 6종
- 목표별 전략 표
- 학습·검증 흐름
- 통합 재고 결과 컬럼
- 공식 계열사·법규·연구 출처

### 재배치

- DB 설명은 AI 입력 데이터 섹션으로 이동한다.
- 수식은 파이프라인의 전략 계산 단계 뒤에 배치한다.
- 계열사 설명은 공통 모델 입력과 정책 프로필을 비교하는 표로 묶는다.
- 학습 설명은 머신러닝 생명주기로 확장한다.

### 제거·수정

- `MVP 비용 프로필`, `이번 MVP`처럼 실제 서비스 범위와 충돌하는 표현을 제거한다.
- 같은 CTA가 중복 표시되는 부분을 하나로 줄인다.
- `Q_available`, `M_inc` 등 사용자용 표에 남은 영문 수식 용어를 한글 중심으로 바꾼다.
- confidence를 예상수량에 직접 곱하는 설명은 사용하지 않는다.
- 계열사별 모델을 처음부터 세 개 만드는 것으로 오해할 표현을 제거한다.
- RAG·벡터 DB가 숫자 계산이나 정형 조회를 담당하는 것으로 오해할 표현을 제거한다.

## 17. 비기능 요구사항

- 동일 snapshot·모델·수식·정책 버전이면 동일 계산 결과를 재현할 수 있어야 한다.
- AI 결과에는 데이터 기준시각과 버전이 항상 포함되어야 한다.
- 계열사 동기화 일부 실패가 다른 계열사의 조회·예측을 중단시키지 않아야 한다.
- LLM이 실패해도 수요예측·위험·전략 수식 결과는 조회할 수 있어야 한다.
- 민감 원가와 계약정보는 설명용 LLM·RAG에 원문으로 전달하지 않는다.
- 사이트 문서에는 실제 운영 전 계열사 데이터 계약과 내부 정책 검증이 필요함을 명시한다.

## 18. 완료 기준

1. `/ai-guide`, `/ai-blueprint`, `/formulas`에서 동일한 통합 가이드를 확인할 수 있다.
2. 페이지 상단에서 전체 AI 처리 순서를 한 번에 이해할 수 있다.
3. 기술별 책임 표에서 ML·수식·LLM·RAG·벡터 DB의 차이를 설명할 수 있다.
4. 전체 필요 데이터가 필수·정확도 향상·후속 고도화로 분류되어 있다.
5. 세 계열사의 공통 입력과 추가 입력·하드 차단·비용 차이를 비교할 수 있다.
6. 최소 12개 상황별 처리 흐름을 확인할 수 있다.
7. 공통 모델과 계열사·카테고리 보정 구조, 모델 분리 조건이 명확하다.
8. 한글 수식에 입력 출처·결과 사용처·누락 처리 방식이 연결되어 있다.
9. 머신러닝 학습·검증·운영·롤백 흐름을 설명할 수 있다.
10. LLM·RAG가 숫자를 결정하지 않는 경계가 명확하다.
11. 최종 출력 필드와 재현 버전을 한 표에서 확인할 수 있다.
12. 실제 서비스와 충돌하는 MVP 표현과 중복 설명이 제거되어 있다.
13. 모바일·키보드·스크린리더에서도 주요 흐름과 펼침 내용을 이용할 수 있다.
14. 기존 사이트 빌드와 정적 페이지 검증이 통과한다.

## 19. 구현 전제와 후속 확정

이 설계는 화면에 표시할 설계 원칙과 데이터 계약을 확정한다. 실제 운영값인 계열사 View 컬럼명, 원가·비용 계약, 예측 기간, 카테고리별 최소 학습량, 위험 가중치, 전략 임계값, LLM 공급자와 문서 접근권한은 구축 과정에서 내부 데이터·정책 담당자와 확정한다. 값이 확정되지 않은 항목은 임의의 숫자를 표시하지 않고 `운영 확정 필요`로 표시한다.
